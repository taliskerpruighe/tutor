# When to use one

*v0.2.0*

That reads like a shortcut for typing into the chat box. It is nearer
the opposite. A headless session cannot answer a clarifying question,
cannot be corrected mid-thought, cannot be shown a second file once the
first answer disappoints you — so it belongs to work you have already
worked out, never to work you are still finding your way through.

Three shapes of that.

## A quick job with no back and forth

Something you would ask a chat and never argue with the answer to.
*"How many words in this draft."* *"Does this paragraph mention the
indemnity clause."* If the honest prediction is that you would read the
reply and move on, a headless session gets there without opening a tab
you will only close again.

## A chain you already trust

*Chain engineering* built something with several agents in it, each
doing one piece, tested until it was reliable. Once a chain is at that
point, sitting and watching it run adds nothing — you already know what
good output looks like, and the chain either produces it or it does not.
Start it headless and read the result when it lands.

## A workflow, minded rather than watched

*What a workflow is* fixed the order in advance: a script calls every
agent, none of it changes on the fly. Nothing about that needs you
present either. Launch a headless agent whose only job is to run the
workflow and tell you how it went — pass or fail, and where — and you
get the workflow's discipline without spending the afternoon reading its
output scroll past.

## The shape that unites them

All three have one thing in common: you could describe, before it runs,
what a good answer looks like. That is the actual test, more than
speed or size of job. If you cannot say what you are hoping to see,
you are still exploring, and exploring wants a chat that can be argued
with.

Getting anything into a headless session, or its answer out of one, is
its own piece of shell grammar.

Press `n`.
